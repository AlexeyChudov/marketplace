# Маркетплейс — REST-сервис на Go с JWT и ролями

## О чём проект

Тот же маркетплейс с листингами, что и в консольной версии, только теперь добавим работу с сетью. Снаружи HTTP и JSON, внутри in-memory хранилище, авторизация по JWT, две роли: продавец создаёт и правит листинги, покупатель их покупает. К сервису прилагается готовый фронтенд, который ты вшиваешь в бинарь и отдаёшь с корня. В конце сервис можно выкатить в облако и дать ссылку живому человеку.

По пути ты соберёшь цепочку middleware, научишься отдавать структурные ошибки валидации, логировать запросы через `slog`, корректно гасить сервер по сигналу и защищать общее состояние от гонок, потому что каждый HTTP-запрос теперь отдельная горутина.

## Чему научишься

После сдачи ты должен понимать и уметь объяснить вслух:

- **HTTP в Go.** Роутинг на `net/http` или chi, чтение тела, параметры пути и query-строки.
- **Middleware.** Цепочка request-id → logger → recover → CORS → auth → require-role → handler, и почему порядок именно такой.
- **JWT на HS256.** Подпись, проверка, `exp`, пара access + refresh.
- **RBAC.** Где проверяется роль (в middleware), а где владение объектом (в handler).
- **Валидация.** Ответ 400 со списком всех проблемных полей, а не первой попавшейся ошибки.
- **`slog`.** JSON-логи запросов со сквозным `request_id`.
- **Graceful shutdown.** `http.Server.Shutdown` по SIGTERM, незавершённые запросы дозавершаются.
- **Конкурентность.** Защита in-memory хранилища от гонок под параллельными запросами.
- **`embed.FS`.** Готовый фронтенд внутри бинаря. Один артефакт, один деплой.
- **Деплой.** Публичный URL, порт из окружения, секреты в переменных.

## Нефункциональные требования

- Роутер на выбор: чистый `net/http`, chi, gin, echo. Библиотека для UUID тоже на выбор, `google/uuid` подходит.
- Код собирается командой `go build .` из корня. Имя бинаря любое, дальше он называется `marketplace-api`.
- Код проходит `gofmt`, `go vet`, `golangci-lint` с конфигом из репозитория и `go test -race`.
- Сервис слушает адрес по правилам ниже и печатает стартовую строку в stdout сразу после старта.
- Без переменной `JWT_SECRET` сервис не стартует: код возврата не ноль, понятное сообщение в stderr.
- Фронтенд из `web/index.html` вшит в бинарь через `embed`. С диска в рантайме он не читается. Тесты запускают бинарь из пустой директории, как контейнер.
- In-memory хранилище выдерживает параллельные запросы без гонок: `go test -race` и тест на 50 параллельных покупок должны быть зелёными.
- Каждый запрос порождает ровно одну строку JSON-лога с заполненным `request_id`.
- По SIGTERM или SIGINT сервис завершается корректно за 10 секунд с кодом 0.
- Структура папок, имена пакетов и типов, формат хранилища на твоё усмотрение. Тесты проверяют только HTTP-поведение.

## Функциональные требования

Сущности:

| Сущность | Поля | Правила |
|---|---|---|
| Пользователь | `id` (uuid), `email`, `password`, `role` | Email уникален. Роль `buyer` или `seller`. Пароль хранится в виде хэша. |
| Листинг | `id` (uuid), `title`, `price`, `stock`, `seller_id`, `created_at` | `title` непустой, `price` больше нуля, `stock` ноль или больше. `seller_id` это создатель. |

Бизнес-логика:

- **Регистрация.** Пользователь передаёт email, пароль и роль. Получает пару токенов и свои данные. Повторный email даёт конфликт.
- **Вход.** По email и паролю выдаётся новая пара токенов. Неверный пароль или неизвестный email дают 401.
- **Обновление токенов.** По refresh-токену выдаётся новая пара. Access-токен на этом роуте не принимается.
- **Создание листинга.** Только продавец. Листинг привязывается к нему.
- **Просмотр.** Список с пагинацией и заголовком с общим количеством, а также один листинг по id. Доступно без токена.
- **Правка и удаление.** Только тот продавец, который создал листинг. Чужой листинг даёт 403 даже продавцу.
- **Покупка.** Только покупатель. Указывает количество, остаток уменьшается. Если товара не хватает, конфликт и остаток не меняется. Под параллельными запросами продать больше, чем есть, нельзя.
- **Фронтенд.** По корневому пути отдаётся готовая страница, которая ходит в этот же API.

## Контракт

Ниже то, что проверяют тесты буквально. Пути, методы, тела, статусы, заголовки, формат ошибок, JWT claims, стартовая строка и набор полей в логе фиксированы.

### Запуск и адрес

```bash
JWT_SECRET=devsecret ./marketplace-api --addr=:8080
```

Адрес выбирается так:

1. Если передан флаг `--addr`, используется он.
2. Иначе, если задана переменная окружения `PORT`, слушаем `:$PORT`.
3. Иначе `:8080`.

Второй пункт нужен для облака: Render, Railway и Fly сами выбирают порт и сообщают его через `PORT`. Слушать нужно на всех интерфейсах, то есть `:8080`, а не `127.0.0.1:8080`, иначе снаружи контейнера до сервиса не достучаться.

Сразу после старта сервис печатает в stdout одну строку:

```
listening on http://127.0.0.1:8080
```

По ней тесты узнают порт. Если `--addr=:0`, печатается реально выбранный порт.

### Роуты

Открытые, токен не нужен:

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/` | Отдаёт фронтенд |
| GET | `/healthz` | `200`, тело `ok` |
| POST | `/auth/register` | Создаёт пользователя |
| POST | `/auth/login` | Выдаёт пару токенов |
| POST | `/auth/refresh` | Обновляет пару по refresh-токену |
| GET | `/listings` | Список листингов с пагинацией |
| GET | `/listings/{id}` | Один листинг |

Приватные, нужен access-токен в заголовке `Authorization: Bearer <token>`:

| Метод | Путь | Кому |
|---|---|---|
| POST | `/listings` | только `seller` |
| PATCH | `/listings/{id}` | только `seller`, создавший листинг |
| DELETE | `/listings/{id}` | только `seller`, создавший листинг |
| POST | `/listings/{id}/buy` | только `buyer` |

Любой другой путь даёт `404` в JSON-формате ошибок, включая `text/plain` заглушки файл-сервера. Корень единственный HTML-роут.

### Эндпоинты подробно

#### `POST /auth/register`

Все три поля обязательны. `role` только `buyer` или `seller`.

```json
// запрос
{"email": "a@a.com", "password": "hunter22", "role": "seller"}
// ответ 201
{"access_token": "...", "refresh_token": "...", "user": {"id": "uuid", "email": "a@a.com", "role": "seller"}}
```

Занятый email даёт `409 conflict`. Плохое тело даёт `400 validation_failed`.

#### `POST /auth/login`

```json
// запрос
{"email": "a@a.com", "password": "hunter22"}
// ответ 200
{"access_token": "...", "refresh_token": "..."}
```

Неверный пароль или несуществующий email дают `401 unauthenticated`. Access и refresh в паре всегда разные строки.

#### `POST /auth/refresh`

```json
// запрос
{"refresh_token": "..."}
// ответ 200
{"access_token": "...", "refresh_token": "..."}
```

Принимает только токен с `typ=refresh`. Access-токен, битый или истёкший токен дают `401`.

#### `POST /listings`

Только `seller`. Все три поля обязательны.

```json
// запрос
{"title": "Молоко", "price": 50.00, "stock": 10}
// ответ 201
{"id": "uuid", "title": "Молоко", "price": 50.00, "stock": 10, "seller_id": "uuid", "created_at": "2025-05-15T10:00:00Z"}
```

Порядок проверок: токен (401), роль (403), тело (400). При невалидном теле в `fields` перечисляются все плохие поля сразу.

#### `GET /listings?limit=20&offset=0`

Оба параметра необязательны. По умолчанию `limit=20`, `offset=0`.

- `limit` от 1 до 100 включительно, иначе `400 validation_failed`.
- `offset` ноль или больше, иначе `400`.
- Порядок строго по `created_at` по возрастанию.
- Заголовок `X-Total-Count` содержит общее число листингов, а не размер страницы.

```
200
X-Total-Count: 42
[{"id":"...","title":"...","price":50.00,"stock":10,"seller_id":"...","created_at":"..."}]
```

#### `GET /listings/{id}`

`200` с телом листинга в том же формате, что при создании. Неизвестный id даёт `404 not_found`.

#### `PATCH /listings/{id}`

Только владелец. Частичное обновление: поля те же, что при создании, каждое необязательно, но присланные проверяются по тем же правилам. Ответ `200` с обновлённым листингом. Чужой листинг даёт `403`, неизвестный id даёт `404`.

#### `DELETE /listings/{id}`

Только владелец. Ответ `204` без тела. Чужой листинг даёт `403`, неизвестный id даёт `404`.

#### `POST /listings/{id}/buy`

Только `buyer`. `qty` обязателен и больше нуля.

```json
// запрос
{"qty": 3}
// ответ 200
{"listing_id": "uuid", "qty": 3, "remaining": 7}
```

Если `qty` больше остатка, `409 conflict`, остаток не меняется. Проверка остатка и его уменьшение должны быть одной атомарной операцией под блокировкой: 50 параллельных покупок по одной штуке при остатке 10 дают ровно 10 успехов и 40 конфликтов.

### JWT

- Алгоритм HS256, секрет из `JWT_SECRET`.
- Claims: `sub` (id пользователя), `role`, `exp`, `iat`, `typ` со значением `access` или `refresh`.
- Access живёт 5 минут. Тест допускает от 1 до 15 минут.
- Refresh живёт 7 дней. Тест требует не меньше суток и строго дольше access.
- Приватные роуты принимают только `typ=access`, refresh-роут только `typ=refresh`.
- Проверяются подпись, `exp` и `typ`. Любая проблема даёт `401`.

Пять минут это намеренно мало. С таким сроком ты за время разработки своими глазами увидишь во фронтенде, как приходит 401 и как страница сама ходит за новым токеном. Хотя у нас и на проде всего 15 мин, что неудобно...

### Формат ошибок

Все ответы 4xx и 5xx имеют одну форму:

```json
{
  "error": "validation_failed",
  "message": "request body is invalid",
  "fields": [
    {"field": "title", "message": "must not be empty"},
    {"field": "price", "message": "must be positive"}
  ]
}
```

`fields` присутствует только при `validation_failed`.

| Статус | `error` | Когда |
|---|---|---|
| 400 | `validation_failed` | плохое тело или query-параметры |
| 401 | `unauthenticated` | нет токена, битый, истёк, не тот `typ`, неверный пароль |
| 403 | `forbidden` | не та роль или не владелец |
| 404 | `not_found` | нет такого листинга или пути |
| 409 | `conflict` | не хватает товара, email занят |
| 500 | `internal` | паника или внутренняя ошибка |

### Middleware

Порядок для приватных роутов: request-id → logger → recover → CORS → auth → require-role → handler. Для открытых те же первые четыре.

1. **request-id.** Берёт `X-Request-ID` из запроса или генерирует UUID. Пишет его в ответный заголовок `X-Request-ID` и в контекст.
2. **logger.** После ответа пишет одну JSON-строку через `slog` уровня INFO с полями `request_id`, `method`, `path`, `status`, `dur_ms`, `remote_addr`. Порядок полей не важен. При статусе 500 и выше уровень ERROR.
3. **recover.** Ловит панику, пишет ERROR в лог и отдаёт `500 internal`. Стоит после logger, чтобы паника попала в лог с `request_id`.
4. **CORS.** `Access-Control-Allow-Origin: *`. Запрос `OPTIONS` с заголовком `Origin` обрабатывается здесь же: ответ 2xx с `Access-Control-Allow-Origin` и `Access-Control-Allow-Methods`, в котором есть `POST`. Дальше в роутер preflight не идёт.
5. **auth.** Разбирает `Authorization`, проверяет JWT, кладёт `user_id` и `role` в контекст. Проблема даёт `401`.
6. **require-role.** Сравнивает роль из контекста с требуемой. Не совпала, `403`.

### Graceful shutdown

- По SIGTERM или SIGINT вызывается `http.Server.Shutdown` с дедлайном 10 секунд.
- Запросы, которые уже выполняются, дозавершаются успешно. Новые соединения не принимаются.
- Процесс выходит с кодом 0. Если за 10 секунд не уложился, ERROR в лог и код 1.

### Фронтенд

`web/index.html` уже готов. Ты его не пишешь и не меняешь, но обязан отдавать:

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/` | `200`, `Content-Type: text/html; charset=utf-8`, содержимое `web/index.html` |

Файл вшивается в бинарь:

```go
import "embed"

//go:embed web/index.html
var webFS embed.FS
```

Дальше либо прочитать его один раз на старте и отдавать байты, либо `http.FileServerFS`. Если используешь файл-сервер, следи, чтобы он не перехватил все неизвестные пути: они по-прежнему должны отдавать JSON-404.

Открой страницу в браузере, держи DevTools → Network. Панель «Что уходит на бэкенд» покажет статус, время и `X-Request-ID` каждого запроса. Это твой собственный middleware, только видимый.

## Тесты

Тесты лежат в `acceptance/`. Это чёрный ящик: они собирают твой бинарь, запускают его на свободном порту из пустой временной директории, ждут стартовую строку и ходят в API через `net/http`. В конце гасят через SIGTERM. `JWT_SECRET` тесты задают сами.

| Тест | Сценарий |
|---|---|
| `TestAcc01_Healthz` | `GET /healthz` даёт 200 без токена. |
| `TestAcc02_RegisterLoginRefresh` | Регистрация, вход, обновление. Токены непустые, access и refresh различаются. |
| `TestAcc03_LoginWrongPassword` | Неверный пароль даёт 401. |
| `TestAcc04_RoleGates` | `POST /listings`: без токена 401, с buyer 403, с seller 201. |
| `TestAcc05_OwnerOnlyEditDelete` | PATCH и DELETE чужого листинга дают 403. Своего дают 200 и 204. |
| `TestAcc06_BuyHappyPath` | Покупка 3 из 10 даёт 200 и `remaining: 7`. |
| `TestAcc07_BuyOversell409` | Покупка больше остатка даёт 409. |
| `TestAcc08_OversellUnderConcurrency` | 50 параллельных покупок по одной при остатке 10: ровно 10 ответов 200 и 40 ответов 409, итоговый stock 0. Главный тест на гонки. |
| `TestAcc09_PaginationAndTotalCount` | `?limit=5&offset=10` даёт 5 строк и правильный `X-Total-Count`. `?limit=999` даёт 400. |
| `TestAcc10_StructuredValidationError` | Плохие title, price и stock в одном запросе: 400, `validation_failed`, все три поля в `fields`. |
| `TestAcc11_JWTExpired` | Токен с истёкшим `exp`, подписанный верным секретом, даёт 401. |
| `TestAcc12_JWTTampered` | Токен с подменённой подписью даёт 401. |
| `TestAcc13_RefreshTokenRejectedOnAccessRoute` | Refresh-токен на приватном роуте даёт 401. |
| `TestAcc14_RequestIDHeaderEcho` | Присланный `X-Request-ID` возвращается в ответе. Без него сервер генерирует свой. |
| `TestAcc15_GracefulShutdown` | SIGTERM во время запросов: они завершаются успешно, процесс выходит с кодом 0 не дольше 11 секунд. |
| `TestAcc16_ServesFrontend` | `GET /` даёт 200, `text/html` и содержимое `web/index.html`. Бинарь при этом запущен из пустой директории. |
| `TestAcc17_UnknownPathStillJSON404` | Неизвестный путь даёт JSON с `error: not_found`, а не текстовую заглушку. |
| `TestAcc18_CORSPreflight` | `OPTIONS /listings` с `Origin` даёт 2xx и заголовки `Access-Control-Allow-*` с `POST`. |
| `TestAcc19_PortFromEnv` | Без `--addr`, но с `PORT=N` сервис слушает `:N`. |
| `TestAcc20_TokenTTLs` | Access живёт от 1 до 15 минут, refresh не меньше суток и дольше access. |

Типичные причины падений:

- **Тест 08.** Нет мьютекса в хранилище, или проверка остатка и его уменьшение не под одной блокировкой.
- **Тест 15.** `os.Exit(0)` сразу по сигналу вместо `Shutdown`, или `Shutdown` без дедлайна.
- **Тесты 11, 12, 13.** Проверяется только подпись, а `exp` или `typ` забыты.
- **Тест 10.** Возвращается первая ошибка валидации вместо списка.
- **Тест 17.** Файл-сервер повешен на `/` и съедает все несматченные пути.
- **Тест 18.** `OPTIONS` пропускается в роутер, где такого метода нет, и получается 405.
- **Тест 16.** Файл читается с диска через `os.ReadFile` вместо `embed`.

### Как запустить

```bash
go build ./...
cd acceptance
MARKETPLACE_SRC=$(pwd)/.. go test -race -v ./...
```

Или с уже собранным бинарём:

```bash
MARKETPLACE_BIN=/path/to/marketplace-api go test -race -v ./...
```

Запустить сервис руками и потыкать фронт:

```bash
JWT_SECRET=test-secret ./marketplace-api --addr=:8080
# открой http://127.0.0.1:8080/
```

CI на каждый push гоняет `gofmt`, `go vet`, `go build`, `go test -race` по твоим пакетам, `golangci-lint` и acceptance-тесты. Зелёный CI означает, что задача принята.

## Деплой

Необязательная часть, но сделать стоит. Пока сервис живёт на localhost, это упражнение. Когда есть ссылка, которую можно отправить человеку, это проект в портфолио.

`Dockerfile` и `render.yaml` уже лежат в репозитории, разбираться в Docker не нужно. Пошаговая инструкция, альтернативные платформы и разбор типичных проблем в `DEPLOY.md`.

## Правила работы с репозиторием

Код пиши в корне репозитория: `main.go` и любые пакеты рядом.

Трогать нельзя:

| Путь | Почему |
|---|---|
| `acceptance/` | Критерий приёмки. CI сверяет содержимое с `.acceptance-manifest.sha256`. |
| `web/` | Готовый фронтенд. Тесты проверяют, что ты отдаёшь именно его. |
| `Dockerfile`, `render.yaml`, `vercel.json` | Готовые конфиги деплоя. Работают как есть. |
| `.github/`, `.golangci.yml`, `.githooks/`, `DEPLOY.md` | Инфраструктура задания. |
| Этот README | Здесь контракт. |

Эти пути закрыты через `CODEOWNERS`: PR, который их меняет, требует ревью ментора.

### Git-хуки

В репозитории лежит pre-commit хук, который перед каждым коммитом прогоняет `gofmt`, `go vet`, `go build` и проверяет, что защищённые файлы не тронуты. Так ты узнаёшь о проблеме до пуша, а не из красного CI.

Git не включает хуки из репозитория сам, поэтому один раз после клонирования выполни:

```bash
make setup
```

Это просто `git config core.hooksPath .githooks`, можно и руками.

## Вопросы на собеседовании

К концу проекта на каждый вопрос нужно отвечать без подсказок. Если на каком-то залип, это и есть твоя следующая тема.

1. **JWT внутри.** Из чего состоит JWT? Что лежит в header, payload и signature? Кто и чем проверяет подпись?
2. **HS256 vs RS256.** Когда выбрать симметричный алгоритм, а когда асимметричный? Кому раздавать какой ключ?
3. **Refresh-токены.** Зачем нужен refresh, если access и так работает? Как инвалидировать refresh при logout? Почему короткий TTL сам по себе не решение?
4. **Где хранить токены на клиенте.** localStorage или httpOnly cookie? XSS против CSRF. Что выберешь для браузерного SPA?
5. **Пароли.** Почему нельзя хранить пароль как есть? bcrypt, argon2, scrypt: почему не MD5 и не SHA256? Что такое salt и pepper?
6. **Порядок middleware.** Если `auth` стоит перед `recover` и handler паникует, что увидит клиент и что попадёт в логи? Почему recover ставят после logger?
7. **Graceful shutdown.** Что делает `http.Server.Shutdown`? Чем отличается от `Close`? Откуда берётся 10-секундный дедлайн и что произойдёт по нему?
8. **Распространение контекста.** В handler запущена горутина с медленной операцией, клиент закрыл соединение. Как горутина об этом узнает? Какой контекст ей передать?
9. **slog vs log.** Чем `log/slog` лучше `log`? Что такое `slog.Handler` и `slog.With`? Как добавить `request_id` во все логи внутри одного запроса?
10. **Гонки в HTTP.** In-memory map листингов без мьютекса, два параллельных POST. Что произойдёт? Какой инструмент Go это покажет?
11. **CORS.** Что такое preflight и когда браузер его шлёт? Почему `Access-Control-Allow-Origin: *` нельзя сочетать с куками? Что будет, если CORS-middleware поставить после auth?
12. **embed.** Чем `//go:embed` лучше чтения с диска для статики? Что попадает в бинарь, а что нет? Как это меняет деплой?
13. **PORT.** Почему облачные платформы навязывают порт через переменную окружения? Почему сервис на `127.0.0.1` работает локально и не работает в контейнере?
